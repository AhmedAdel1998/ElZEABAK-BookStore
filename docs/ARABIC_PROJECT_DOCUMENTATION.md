# التوثيق الشامل لمشروع BookStore POS

## 1. مقدمة عامة

`BookStore POS` هو تطبيق سطح مكتب لإدارة مكتبة ونقطة بيع، مبني بتقنية WPF على .NET 9، ويعمل محليا على Windows. التطبيق مصمم لإدارة العمليات اليومية داخل مكتبة أو متجر كتب: المنتجات، التصنيفات، العملاء، الموردين، المخزون، البيع من الكاشير، الإيصالات، التقارير، الإعدادات، النسخ الاحتياطي، وسجل التدقيق.

التطبيق في حالته الحالية هو تطبيق محلي/أوفلاين. معنى ذلك أن البيانات تحفظ في قاعدة SQLite على جهاز التشغيل، وليس في خادم مركزي أو سحابة. إذا تم تثبيته على جهاز عميل واحد، فكل بيانات العميل ستكون على هذا الجهاز. إذا احتاج العميل إلى أكثر من جهاز يشاركون نفس المنتجات والمبيعات والمخزون، فذلك يحتاج إلى مرحلة مختلفة تشمل خادم أو مزامنة بيانات، ولا يكفي نسخ البرنامج فقط بين الأجهزة.

## 2. الهدف من المشروع

الهدف العملي للمشروع هو توفير نظام POS مخصص للمكتبات، بحيث يستطيع صاحب المكتبة أو الموظفون تنفيذ دورة العمل اليومية كاملة:

- إنشاء التصنيفات والمنتجات.
- إدخال بيانات الكتب والأسعار والباركود والمخزون.
- ربط المنتجات بالموردين.
- تسجيل العملاء وربط العميل بفاتورة بيع عند الحاجة.
- تشغيل شاشة بيع سريعة للكاشير.
- مسح الباركود أو البحث عن المنتج.
- إضافة المنتجات إلى الفاتورة.
- تطبيق خصومات على البند أو الفاتورة.
- حساب الضريبة والإجمالي والباقي.
- إتمام البيع وتخفيض المخزون تلقائيا.
- طباعة إيصال البيع أو إعادة طباعته لاحقا.
- متابعة التقارير اليومية وتقارير الربح والمخزون والعملاء والكاشير.
- عمل نسخ احتياطي واسترجاع آمن لقاعدة البيانات.
- مراقبة جودة البيانات وسجل العمليات المهمة.

## 3. طبيعة التطبيق الحالية

التطبيق ليس Web Application، وليس Mobile Application، وليس خدمة Cloud. هو تطبيق Desktop يعمل على Windows من خلال ملف تنفيذي `BookStore.UI.exe`.

الواجهة الرسومية مبنية بـ WPF. منطق الأعمال مفصول في طبقات داخلية. قاعدة البيانات SQLite، ويتم إنشاؤها وتحديثها محليا عند تشغيل التطبيق. ملفات التشغيل مثل قاعدة البيانات واللوجات والنسخ الاحتياطية توضع في مجلد بيانات قابل للكتابة، وليس بالضرورة في مجلد تثبيت البرنامج.

## 4. التقنيات المستخدمة

التقنيات الأساسية:

- .NET 9.
- WPF لواجهة سطح المكتب.
- Entity Framework Core مع SQLite.
- Clean Architecture لتقسيم المسؤوليات.
- MVVM في واجهة المستخدم.
- CQRS على مستوى أوامر واستعلامات التطبيق.
- FluentValidation للتحقق من المدخلات.
- AutoMapper لتحويل الكيانات إلى DTOs ونماذج واجهة.
- Microsoft.Extensions.Hosting لتشغيل Host داخل تطبيق WPF.
- Serilog للـ logging.
- BCrypt لتخزين كلمات المرور كـ hash آمن.
- Windows Data Protection لحفظ `Remember Me` محليا بشكل مشفر.

## 5. الحلول والمشاريع داخل الـ Solution

المشروع الرئيسي موجود داخل solution باسم `BookStore.sln`. البنية الأساسية للمشروع مقسمة إلى:

- `BookStore.Domain`: الكيانات وقواعد الأعمال الأساسية.
- `BookStore.Application`: أوامر واستعلامات التطبيق، DTOs، Validators، وواجهات الخدمات.
- `BookStore.Persistence`: قاعدة البيانات، EF Core، الـ migrations، repositories، Unit of Work، والـ seeding.
- `BookStore.Infrastructure`: الخدمات العملية مثل تسجيل الدخول، الطباعة، الباركود، النسخ الاحتياطي، إعداد المجلدات، وحفظ جلسات POS المؤقتة.
- `BookStore.Reporting`: تقارير وتحليلات وData Quality وAudit Trail.
- `BookStore.Shared`: الثوابت، الموديلات المشتركة، نتائج العمليات، ومسارات البيانات.
- `BookStore.UI`: تطبيق WPF والـ ViewModels والـ Views والـ Themes والـ Navigation.
- `tests`: اختبارات Domain وApplication وInfrastructure وUI.

## 6. الاعتمادية بين الطبقات

المشروع يستخدم Clean Architecture بحيث لا تعتمد الطبقات الداخلية على الطبقات الخارجية.

الاتجاه العام:

- `Domain` هو المركز ولا يعتمد على المشاريع الأخرى.
- `Application` يعتمد على `Domain` ويعرف أوامر واستعلامات وواجهات الخدمات.
- `Persistence` يعتمد على `Domain` و`Shared` لتنفيذ التخزين.
- `Infrastructure` يعتمد على `Application` و`Shared` لتنفيذ الخدمات الخارجية/العملية.
- `Reporting` يستخدم `Application` و`Domain` و`Persistence` للقراءة والتحليل.
- `UI` يركب كل الطبقات ويجمعها داخل الـ DI container.

هذه البنية مهمة لأن واجهة WPF لا يجب أن تحتوي منطق قاعدة بيانات مباشر أو قواعد أعمال عميقة. الواجهة تستدعي ViewModels، والـ ViewModels تستدعي Handlers/Services، وهذه بدورها تتعامل مع Unit of Work والـ Repositories.

## 7. دورة تشغيل التطبيق من أول ضغط على البرنامج

عند تشغيل `BookStore.UI.exe` يحدث ما يلي:

1. يبدأ تطبيق WPF من `App.xaml.cs`.
2. يتم تجهيز معالجة الأخطاء العامة حتى لا يسقط التطبيق بدون رسالة مفهومة.
3. يتم إنشاء Bootstrap Logger في مجلد اللوجات.
4. يتم إنشاء Host باستخدام `Host.CreateDefaultBuilder`.
5. يتم تحميل `appsettings.json`.
6. يتم تحميل متغيرات البيئة التي تبدأ بـ `BOOKSTORE_`.
7. يتم تسجيل الخدمات في DI:
   - `AddApplication`.
   - `AddPersistence`.
   - `AddInfrastructure`.
   - `AddReporting`.
   - `AddPresentation`.
8. يبدأ الـ Host.
9. يعمل `DatabaseInitializer` كـ Hosted Service.
10. يتم إنشاء مجلد قاعدة البيانات إذا لم يكن موجودا.
11. يتم ضبط SQLite بـ:
    - Foreign Keys.
    - Busy Timeout.
    - WAL Mode.
12. يتم تطبيق EF Core migrations تلقائيا.
13. يتم تنفيذ seed للأدوار والصلاحيات والتصنيفات الأساسية.
14. يتم التأكد من وجود مجلدات التشغيل المطلوبة.
15. يتم تطبيق اللغة والثيم والعملة.
16. يفحص التطبيق هل توجد أي مستخدمين.
17. إذا لا توجد مستخدمين، يفتح شاشة First Run Setup لإنشاء أول Administrator.
18. إذا يوجد مستخدمون، يحاول استرجاع جلسة Remember Me.
19. إذا فشل الاسترجاع يفتح شاشة Login.
20. بعد تسجيل الدخول يفتح الـ Authenticated Shell والـ Dashboard.

## 8. مسارات ملفات البيانات

التطبيق لا يجب أن يكتب بياناته داخل مجلد التثبيت لأن مجلد مثل `C:\Program Files` غالبا يكون للقراءة فقط للمستخدم العادي.

مسار البيانات يحسب كالتالي:

- إذا كان متغير البيئة `BOOKSTORE_DATA_DIR` مضبوطا، يستخدم التطبيق هذا المسار.
- إذا لم يكن مضبوطا، يستخدم:
  `%LOCALAPPDATA%\BookStore POS`

داخل مجلد البيانات توجد مجلدات تشغيل:

- `Database`: قاعدة SQLite.
- `Logs`: ملفات اللوج.
- `Backups`: النسخ الاحتياطية.
- `Exports`: الملفات المصدرة.
- `Temp`: الملفات المؤقتة، مثل جلسات POS المفتوحة وملف Remember Me.

قاعدة البيانات الافتراضية اسمها:

```text
Database/bookstore.db
```

لكن هذا المسار يتحول إلى مسار فعلي تحت مجلد بيانات التطبيق.

## 9. التهيئة الأولى First Run Setup

إذا كانت قاعدة البيانات لا تحتوي أي مستخدمين، يعتبر التطبيق أنه في أول تشغيل.

في هذه الحالة يفتح شاشة إنشاء أول مدير للنظام. هذا الحساب يحصل على دور `Administrator`. شروط كلمة المرور في أول إعداد:

- كلمة المرور لا تقل عن 8 أحرف.
- تحتوي حرف كبير.
- تحتوي حرف صغير.
- تحتوي رقم.
- تحتوي رمز خاص.
- تأكيد كلمة المرور مطابق.

التطبيق لا يشحن كلمة مرور Administrator ثابتة افتراضيا. هذا قرار أمني مهم. يمكن تهيئة admin أولي من الإعدادات فقط إذا تم وضع `Application:InitialAdmin` مع `PasswordHash` من نوع BCrypt، لكن الاستخدام الطبيعي الأفضل هو شاشة First Run Setup ثم إزالة أي إعداد تهيئة أولية بعد ذلك.

## 10. تسجيل الدخول والجلسة

تسجيل الدخول يتم من خلال `AuthenticationService`.

دورة تسجيل الدخول:

1. المستخدم يدخل اسم المستخدم وكلمة المرور.
2. يتم التحقق من صحة شكل الطلب.
3. يتم البحث عن المستخدم بالـ username.
4. إذا المستخدم غير موجود تظهر رسالة فشل عامة.
5. إذا المستخدم غير نشط يرفض الدخول.
6. إذا الحساب مقفول مؤقتا يرفض الدخول حتى وقت انتهاء القفل.
7. إذا كلمة المرور خطأ:
   - يزيد عدد المحاولات الفاشلة.
   - إذا وصل للحد الأقصى يتم قفل الحساب مؤقتا.
   - يتم تسجيل حدث في Audit Trail.
8. إذا كلمة المرور صحيحة:
   - يتم تصفير محاولات الفشل.
   - يتم عمل rehash إذا كان الـ hash يحتاج تحديثا.
   - يتم إنشاء Session Snapshot.
   - يتم تحميل الدور والصلاحيات داخل الجلسة.
   - يمكن حفظ Remember Me حسب اختيار المستخدم.

إعدادات الحماية الافتراضية:

- الحد الأقصى لمحاولات تسجيل الدخول: 5.
- مدة القفل: 15 دقيقة.
- مدة جلسة عدم النشاط: 30 دقيقة.
- Remember Me: 30 يوما.

## 11. Remember Me

ميزة Remember Me تحفظ معرف المستخدم في ملف محلي مشفر داخل مجلد `Temp`. التشفير يعتمد على Windows Data Protection وبنطاق `CurrentUser`. هذا يعني أن الملف لا يصلح عادة لمستخدم Windows آخر ولا لجهاز آخر.

عند بداية التشغيل يحاول التطبيق قراءة الملف:

- إذا الملف غير موجود، يفتح Login.
- إذا الملف انتهت صلاحيته، يحذفه ويفتح Login.
- إذا الملف تالف أو غير قابل لفك التشفير، يحذفه ويفتح Login.
- إذا المستخدم غير موجود أو غير نشط أو مقفول، يحذف التذكر ويفتح Login.
- إذا كل شيء صحيح، يدخل المستخدم مباشرة.

## 12. الأدوار والصلاحيات

التطبيق يحتوي على ثلاثة أدوار أساسية:

- `Administrator`: صلاحية كاملة.
- `Manager`: صلاحيات إدارة المتجر مع استثناءات إدارية حساسة مثل إدارة المستخدمين والأدوار واسترجاع النسخ الاحتياطية.
- `Cashier`: صلاحيات كاشير، مثل إنشاء وإتمام وتعليق البيع، عرض المنتجات والتصنيفات والمخزون، التعامل مع العملاء، وطباعة الإيصالات.

الصلاحيات مخزنة كأسماء ثابتة في `PermissionCatalog`. عند تشغيل التطبيق يتم التأكد أن الصلاحيات الجديدة موجودة في قاعدة البيانات، وأن أدوار Administrator وManager وCashier حصلت على الصلاحيات المناسبة.

أمثلة على مجموعات الصلاحيات:

- منتجات: عرض، إنشاء، تعديل، حذف، تصدير، استيراد.
- تصنيفات: عرض، إنشاء، تعديل، حذف.
- مبيعات: إنشاء، إتمام، تعليق، إلغاء، خصم، تجاوز سعر، عرض تاريخ.
- مخزون: عرض، تعديل، تسوية، تاريخ، تصدير.
- باركود: عرض، توليد، طباعة، إعدادات.
- عملاء: عرض، إنشاء، تعديل، حذف، تاريخ مشتريات.
- موردون: عرض، إنشاء، تعديل، حذف، عرض منتجات المورد.
- تقارير: لوحة تقارير، مبيعات، أرباح، مخزون، عملاء، كاشير، تصدير.
- إيصالات: طباعة، إعادة طباعة، اختبار طباعة، إعدادات.
- إعدادات: متجر، POS، إيصال، طابعة، ضريبة، عملة، باركود، مخزون، نسخ احتياطي، أمان، مظهر.
- نسخ احتياطي: عرض، إنشاء، استرجاع، حذف، تحقق، إعدادات.
- سجل تدقيق وجودة بيانات: عرض.

- مركز إشعارات مؤقتة.

القائمة الجانبية لا تعرض أو لا تتيح بعض المسارات إلا حسب صلاحيات المستخدم. أهم عناصر القائمة:

- Dashboard.
- Categories.
- Products.
- Inventory.
- Barcode.
- Sales/POS.
- Customers.
- Suppliers.
- Reports.
- Settings.
- Backup.
- Audit/History.
- Data Quality/Validate.

## 14. Dashboard

لوحة التحكم تعرض ملخصا تشغيليا مبنيا على تقارير اليوم والمخزون.

تعرض مؤشرات مثل:

- مبيعات اليوم.
- عدد معاملات اليوم.
- قيمة المخزون بسعر البيع.
- المنتجات قليلة المخزون.
- ربح اليوم.
- المنتجات المنتهية من المخزون.
- قيمة الشراء للمخزون.
- خصومات اليوم.
- أفضل منتج مبيعا.
- أفضل عميل.
- أفضل كاشير.
- حالة المخزون.
- مقارنة مبيعات اليوم بالأمس.

بعض بطاقات Dashboard قابلة للضغط وتنقل المستخدم إلى الشاشة المناسبة إذا لديه الصلاحية:

- مبيعات اليوم إلى Sales Summary.
- معاملات اليوم إلى Sales Details.
- الربح إلى Profit Report.
- قيمة المخزون إلى Inventory Report.
- قليل المخزون إلى Inventory List مع فلتر Low Stock.
- منتهي المخزون إلى Inventory List مع فلتر Out of Stock.

يوجد أيضا Quick Actions حسب الصلاحيات:

- فتح POS.
- المنتجات.
- المخزون.
- التقارير.
- حالة النسخ الاحتياطي.

## 15. إدارة التصنيفات Categories

التصنيف يمثل مجموعة للمنتجات، مثل Programming أو Novels أو Education.

وظائف التصنيفات:

- عرض التصنيفات.
- البحث في التصنيفات.
- إنشاء تصنيف جديد.
- تعديل الاسم والوصف.
- تفعيل أو تعطيل التصنيف.
- حذف منطقي حسب مسار التطبيق وقواعد الحذف.

قواعد التصنيف:

- الاسم مطلوب.
- الاسم لا يزيد عن 100 حرف.
- التصنيف يمكن أن يكون Active أو Inactive.
- المنتجات مرتبطة بتصنيف واحد من خلال `CategoryId`.

## 16. إدارة المنتجات Products

المنتج هو العنصر الأساسي القابل للبيع. في سياق المشروع المنتج غالبا كتاب، لذلك يدعم حقول كتب كثيرة.

بيانات المنتج:

- Barcode.
- ISBN اختياري.
- Title.
- Subtitle.
- Description.
- Author.
- Publisher.
- Language.
- Edition.
- PublishDate.
- PurchasePrice.
- SellingPrice.
- TaxCategory.
- Quantity.
- MinimumStock.
- ShelfLocation.
- ImagePath.
- CategoryId.
- IsActive.

وظائف المنتجات:

- عرض قائمة المنتجات.
- البحث والفلترة.
- إنشاء منتج.
- تعديل منتج.
- فتح تفاصيل منتج.
- تكرار منتج مع باركود جديد.
- تفعيل أو تعطيل منتج.
- حذف منتج.
- عرض المنتجات قليلة المخزون.

قواعد المنتج:

- الباركود مطلوب وفريد.
- ISBN إذا أدخل يجب أن يكون صحيحا وغير مكرر.
- العنوان مطلوب.
- المؤلف مطلوب.
- سعر الشراء لا يكون سالبا.
- سعر البيع لا يكون سالبا.
- الكمية لا تكون سالبة.
- الحد الأدنى للمخزون لا يكون سالبا.
- التصنيف مطلوب.
- صورة المنتج إن وجدت يجب أن تكون JPG أو PNG أو WEBP.
- حجم الصورة لا يتجاوز 5MB.
- المنتج غير النشط لا يباع داخل POS.
- المنتج لا يسمح له بكمية سالبة في قواعد الـ Domain.

## 17. إدارة المخزون Inventory

المخزون مرتبط مباشرة بكمية المنتج. كل حركة مخزون تسجل في جدول `InventoryTransactions`.

وظائف المخزون:

- عرض لوحة مخزون.
- عرض قائمة المخزون.
- البحث حسب المنتج أو التصنيف.
- عرض قليل المخزون فقط.
- عرض المنتهي من المخزون فقط.
- زيادة كمية منتج.
- تقليل كمية منتج.
- تسوية الكمية إلى قيمة محددة.
- عرض تاريخ الحركات.

أنواع الحركات المعرفة في النظام:

- `InitialStock`: إدخال مخزون أولي.
- `ManualAdjustment`: تسوية يدوية.
- `Sale`: بيع منتج من POS.
- `Return`: إرجاع منتج.
- `Damage`: مخزون تالف.
- `Correction`: تصحيح مخزون.
- `Purchase`: شراء/توريد، وهو محجوز لاستخدامات أوامر الشراء المستقبلية.
- `Adjustment`: اسم قديم يشير إلى `ManualAdjustment`.

كل حركة مخزون تحفظ:

- ProductId.
- Quantity كتغير موجب أو سالب.
- TransactionType.
- QuantityBefore.
- QuantityAfter.
- Reason.
- Reference مثل رقم الفاتورة.
- UserId.
- UserName.
- Notes.
- Date.

عند إتمام بيع POS يتم إنشاء حركة مخزون من نوع Sale بكمية سالبة لكل منتج تم بيعه. السبب يكون `POS sale` والمرجع يكون رقم الفاتورة.

قواعد العملاء:

## 21. POS ودورة البيع الكاملة

شاشة POS هي قلب التطبيق التشغيلي. هدفها أن يعمل الكاشير بسرعة بالباركود أو البحث، مع الحفاظ على دقة المخزون والفواتير.

### 21.1 فتح فاتورة جديدة

عند فتح شاشة POS:

1. يحاول التطبيق استرجاع الفاتورة المفتوحة الحالية.
2. إذا توجد فاتورة مفتوحة، يعيد فتحها بدلا من إنشاء فاتورة فارغة جديدة.
3. إذا طلب المستخدم فاتورة جديدة صراحة، ينشئ فاتورة جديدة طالما لم يتجاوز الحد الأقصى للفواتير المفتوحة.
4. يتم توليد رقم فاتورة مثل:

```text
POS-yyyyMMddHHmmssfff-XXXX
```

5. تحفظ الفاتورة المؤقتة في ملف محلي داخل `Temp/pos-sales.json`.

### 21.2 الفواتير المفتوحة والمعلقة

التطبيق يدعم أكثر من فاتورة مفتوحة على نفس محطة العمل. هذا مهم إذا كان الكاشير يخدم أكثر من عميل أو يحتاج تعليق فاتورة.

المفاهيم:

- Open Invoice: فاتورة مفتوحة في الشريط/الجلسة.
- Active Invoice: الفاتورة المعروضة حاليا.
- Held/Suspended Sale: فاتورة معلقة خارج الفواتير المفتوحة ويمكن استرجاعها.

عند تعليق فاتورة:

- تزال من الفواتير المفتوحة.
- تحفظ في قائمة الفواتير المعلقة.
- يمكن استرجاعها لاحقا.

### 21.3 إضافة منتج إلى الفاتورة

يمكن إضافة منتج بالبحث أو الباركود.

الخطوات الداخلية:

1. يتحقق النظام من وجود فاتورة مفتوحة.
2. يبحث عن المنتج.
3. يتحقق أن المنتج موجود.
4. يتحقق أن المنتج Active.
5. يحسب الكمية المتاحة لهذا المنتج.
6. يأخذ في الاعتبار الكميات المحجوزة في فواتير أخرى مفتوحة.
7. إذا الكمية المطلوبة أكبر من المتاحة يرفض الإضافة برسالة واضحة.
8. إذا المنتج موجود بالفعل في الفاتورة، يزيد كميته.
9. إذا غير موجود، يضيف بندا جديدا.
10. يعيد حساب الإجماليات والضريبة والخصومات.
11. يحفظ الفاتورة المؤقتة.

### 21.4 حماية المخزون بين الفواتير المفتوحة

إذا كان المنتج كميته 1 فقط، وفتحت فاتورتين في POS، لا يسمح التطبيق للفواتير المفتوحة كلها ببيع نفس النسخة. `PosCartStockService` يحسب المحجوز في الفواتير الأخرى، ويطرح ذلك من كمية المنتج قبل السماح بإضافة كمية جديدة.

عند العودة إلى فاتورة مفتوحة قديمة، يزامن التطبيق السلة مع المخزون الحالي:

- إذا المنتج أصبح غير متاح، يحذف البند.
- إذا الكمية المتاحة أقل من كمية السلة، يخفض الكمية.
- إذا المنتج تم تعطيله أو حذفه، يزيله من السلة.

### 21.5 تعديل الكمية

عند تعديل كمية بند:

1. يتحقق النظام من الفاتورة والبند.
2. يحسب الكمية المتاحة الحقيقية الآن.
3. يمنع تجاوز المخزون المتاح.
4. يحدث الكمية.
5. يعيد حساب الفاتورة.
6. يحفظ الفاتورة المؤقتة.

### 21.6 حذف بند

حذف بند من الفاتورة:

- يزيله من السلة.
- يعيد حساب الإجمالي.
- يحفظ الفاتورة.

### 21.7 الخصومات

يوجد نوعان من الخصومات:

- خصم على بند محدد.
- خصم على الفاتورة بالكامل.

قواعد الخصم:

- الخصم يحتاج صلاحية `Sales.ApplyDiscount`.
- الخصم لا يكون سالبا.
- خصم البند لا يتجاوز إجمالي البند.
- خصم الفاتورة لا يتجاوز صافي الفاتورة.
- بعد الخصم يعاد توزيع التأثير على حساب الضريبة بشكل صحيح.

### 21.8 الضريبة والإجمالي

حساب الفاتورة يتم في `PricingService`.

الخطوات:

1. حساب إجمالي كل بند قبل الخصم.
2. حساب خصومات البنود.
3. حساب صافي البنود.
4. تطبيق خصم الفاتورة على الأساس الخاضع للضريبة.
5. حساب الضريبة حسب إعدادات الضريبة.
6. إذا السعر شامل الضريبة، يتم استخراج الضريبة من السعر ولا تضاف مرة أخرى.
7. إذا السعر غير شامل، تضاف الضريبة إلى الإجمالي.
8. يتم التقريب إلى رقمين عشريين بطريقة Retail rounding.
9. يحسب Grand Total.
10. يحسب الباقي Change من Amount Paid.

### 21.9 الدفع

الفاتورة تحتوي:

- PaymentMethod.
- AmountPaid.
- ReceiptCopies.
- GrandTotal.
- Change.

طرق الدفع المعرفة في النظام:

- `Cash`: نقدي.
- `Card`: بطاقة.
- `MobileWallet`: محفظة إلكترونية.
- `BankTransfer`: تحويل بنكي.

الدفع النقدي هو الافتراضي. زر `Pay Exact` يضع المبلغ المدفوع مساويا للإجمالي.

### 21.10 إتمام البيع

عند الضغط على Complete Sale:

1. الواجهة تطلب تأكيد من المستخدم.
2. يمنع النظام تشغيل عمليتي Checkout في نفس الوقت على نفس محطة العمل.
3. يتحقق من صلاحية `Sales.Complete`.
4. يتحقق من صحة الطلب.
5. يتحقق أن الفاتورة تحتوي بنودا.
6. يعيد حساب الإجمالي.
7. يتحقق أن المدفوع لا يقل عن الإجمالي.
8. يبدأ Transaction في Unit of Work.
9. ينشئ كيان `Sale`.
10. يربط العميل إن وجد.
11. لكل بند:
    - يحمل المنتج من قاعدة البيانات.
    - يتأكد أن المنتج Active.
    - يتأكد أن كمية المنتج تكفي.
    - يضيف `SaleItem`.
    - يخفض كمية المنتج.
    - ينشئ `InventoryTransaction` من نوع Sale.
12. يطبق الخصم والضريبة.
13. يحدد طريقة الدفع.
14. يجعل البيع Completed.
15. يحفظ البيع وحركات المخزون.
16. يعمل Commit.
17. يغلق الفاتورة المؤقتة التي تم دفعها.
18. يحاول طباعة الإيصال.

نقطة مهمة: إذا فشلت الطباعة بعد نجاح حفظ البيع، لا يتم إلغاء البيع. البيع يظل محفوظا ويمكن إعادة طباعة الإيصال.

### 21.11 اختصارات POS

الواجهة تحتوي اختصارات لوحة مفاتيح:

- `F2`: فاتورة جديدة.
- `F3`: تعليق الفاتورة.
- `F8`: دفع المبلغ بالضبط.
- `F9`: إتمام البيع.
- `Delete`: حذف بند.
- `Escape`: إلغاء/خروج حسب سياق الشاشة.

كذلك تحافظ شاشة POS على تركيز خانة الباركود حتى يظل الماسح يعمل بسرعة أثناء ضغط الأزرار أو اختيار صفوف.

## 24. النسخ الاحتياطي والاسترجاع Backup and Restore

وحدة النسخ الاحتياطي مصممة لحماية قاعدة SQLite المحلية.

وظائفها:

- إنشاء نسخة احتياطية يدوية.
- إنشاء نسخة تلقائية عند الاستحقاق.
- عرض قائمة النسخ.
- عرض تفاصيل نسخة.
- التحقق من سلامة نسخة.
- حذف نسخة.
- تنظيف النسخ القديمة حسب Retention.
- استرجاع نسخة.
- فحص صحة قاعدة البيانات.

### 24.1 إنشاء Backup

عند إنشاء نسخة:

1. يقرأ التطبيق إعدادات النسخ الاحتياطي.
2. يمنع تشغيل عمليتي Backup/Restore في نفس الوقت.
3. يتحقق أن قاعدة البيانات موجودة.
4. ينشئ مجلد النسخ إذا غير موجود.
5. يتحقق من المساحة المتاحة.
6. ينشئ Metadata للنسخة:
   - BackupId.
   - FileName.
   - CreatedAt.
   - BackupType.
   - ApplicationVersion.
   - DatabaseVersion.
   - CreatedBy.
   - MachineName.
7. يستخدم SQLite `BackupDatabase` وليس نسخ ملف خام.
8. يحسب SHA-256 checksum.
9. يتحقق من integrity.
10. يكتب ملف `.meta.json` بجانب ملف `.db`.

### 24.2 التحقق من Backup

التحقق يشمل:

- وجود ملف النسخة.
- القدرة على فتح الملف للقراءة.
- مطابقة SHA-256 إذا موجود.
- تشغيل `PRAGMA integrity_check`.
- التأكد من وجود الجداول المطلوبة:
  - Products.
  - Sales.
  - InventoryTransactions.
  - Users.

### 24.3 الاسترجاع Restore

الاسترجاع عملية حساسة وتحتاج نص تأكيد حرفي:

```text
I understand that restoring will replace the current database.
```

خطوات الاسترجاع:

1. يتحقق من نص التأكيد.
2. يقفل عمليات النسخ/الاسترجاع الأخرى.
3. يحمل النسخة المختارة.
4. يتحقق من سلامتها.
5. يتحقق من المساحة المتاحة في Temp.
6. ينشئ نسخة PreRestore أولا إذا الإعداد مفعل.
7. ينسخ النسخة إلى ملف مؤقت.
8. يتحقق من الملف المؤقت.
9. يوقف تجمع اتصالات SQLite.
10. يستبدل قاعدة البيانات الحالية باستخدام `File.Replace` إن أمكن.
11. يتحقق من القاعدة بعد الاستبدال.
12. إذا فشل الاستبدال يحاول الرجوع للنسخة السابقة أو PreRestore.
13. يرجع نتيجة تطلب إعادة تشغيل التطبيق.

بعد Restore يجب إغلاق التطبيق وفتحه من جديد قبل متابعة العمل، حتى لا تستمر DbContexts قديمة على بيانات مستبدلة.

### 24.4 النسخ التلقائي

يوجد Hosted Service ينتظر عدة ثوان بعد بدء التطبيق ثم:

- ينظف ملفات restore/rollback المؤقتة المتروكة.
- يشغل النسخ التلقائي إذا كان مستحقا حسب إعدادات Backup.

## 25. الإعدادات Settings

الإعدادات مقسمة إلى مجموعات:

- Store.
- POS.
- Receipt.
- Printer.
- Tax.
- Currency.
- Barcode.
- Inventory.
- Backup.
- Security.
- Appearance.
- Application.

المصدر الأول للإعدادات هو `appsettings.json`. بعد ذلك يمكن حفظ overrides داخل جدول `ApplicationSettings` في قاعدة البيانات.

الخدمة `SettingsService` تقوم بـ:

- قراءة الإعدادات.
- استخدام cache لبعض الأنواع كثيرة الاستخدام.
- حفظ إعدادات جديدة داخل قاعدة البيانات.
- التحقق من الإعدادات عبر Validators.
- إرسال إشعار SettingsChanged عند التغيير.

## 32. قاعدة البيانات

قاعدة البيانات SQLite وتدار عبر EF Core Migrations.

الجداول الرئيسية:

- Categories.
- Products.
- Customers.
- Suppliers.
- ProductSuppliers.
- Users.
- Roles.
- Permissions.
- Sales.
- SaleItems.
- InventoryTransactions.
- ApplicationSettings.
- AuditLogEntries.

توجد Soft Delete query filters للكيانات التي تطبق `ISoftDelete`. هذا يعني أن بعض العناصر المحذوفة لا تظهر في الاستعلامات العادية، لكنها قد تظل موجودة للحفاظ على تاريخ البيانات.

في التقارير التاريخية، بعض الاستعلامات تستخدم `IgnoreQueryFilters` حتى لا تختفي مبيعات قديمة بسبب حذف أو تعطيل منتج لاحقا.

## 33. الترحيلات Migrations

عند بدء التطبيق يتم تشغيل:

```csharp
dbContext.Database.MigrateAsync()
```

هذا يعني أن قاعدة بيانات العميل يتم تحديثها تلقائيا إلى آخر schema موجود في التطبيق المنشور.

مهم قبل نشر إصدار جديد:

- مراجعة migrations.
- اختبار الترقية على نسخة من قاعدة حقيقية.
- أخذ Backup قبل التشغيل على جهاز العميل.
- التأكد أن migration لا يكسر بيانات قديمة.

## 38. القيود الحالية

قيود يجب معرفتها قبل البيع أو التسليم:

- التطبيق محلي/أوفلاين ولا يزامن بين أجهزة متعددة.
- لا توجد خدمة Cloud أو API مركزية حاليا.
- الربح التاريخي لا يخزن تكلفة الشراء وقت البيع، بل يستخدم سعر الشراء الحالي.
- بعض أحداث Audit Trail لم تغط كل وحدات النظام بعد.
- اختبار الطابعة والباركود يحتاج أجهزة حقيقية.
- Publish profile موجود، لكن installer نفسه غير موجود داخل المشروع حاليا.
- Restore production-like لم يتم إثباته بالكامل على نسخة حقيقية في التدقيق السابق.
- Performance benchmark على جهاز العميل لم يتم تسجيله بعد.

2. توليد باركود أو إدخال باركود موجود.
3. إنشاء المنتج مع العنوان والمؤلف والأسعار والتصنيف.

## 41. دورة حياة الفاتورة

حالات الفاتورة:

- Pending: فاتورة مفتوحة قابلة للتعديل.
- Suspended: فاتورة معلقة.
- Completed: فاتورة مكتملة ومحفوظة في قاعدة البيانات.
- Cancelled: فاتورة ملغاة، حسب مسارات الإلغاء المتاحة.

الفاتورة تبدأ كجلسة مؤقتة في POS، وليست `Sale` محفوظة نهائيا في قاعدة البيانات. عند Complete تتحول إلى `Sale` و`SaleItems` وتؤثر على المخزون.

## 42. دورة حياة النسخة الاحتياطية

دورة Backup:

1. إنشاء النسخة.
2. حفظ ملف `.db`.
3. حفظ `.meta.json`.
4. حساب checksum.
5. التحقق من integrity.
6. ظهور النسخة في قائمة Backups.
7. يمكن Validate لاحقا.
8. يمكن Delete إذا ليست آخر نسخة صالحة.
9. يمكن Restore بعد نص تأكيد.
10. بعد Restore يجب Restart.

## 45. ملخص تنفيذي

`BookStore POS` نظام مكتبة محلي قوي نسبيا، جاهز كقاعدة تشغيل لعميل يستخدم جهاز Windows واحد أو عدة مستخدمين على نفس الجهاز مع ضبط مجلد بيانات مشترك. أهم دورة فيه هي POS: فتح فاتورة، إضافة منتجات، حساب ضريبة وخصومات، إتمام البيع، خفض المخزون، وطباعة الإيصال.

قبل تسليمه تجاريا يجب عمل installer واختبار publish output على جهاز حقيقي، خصوصا الطابعة والباركود والنسخ الاحتياطي والاسترجاع. وإذا كان العميل يحتاج أكثر من جهاز يعملون على نفس قاعدة البيانات، فهذه ليست مسألة تثبيت فقط، بل تحتاج تصميم مزامنة أو Backend مركزي.
